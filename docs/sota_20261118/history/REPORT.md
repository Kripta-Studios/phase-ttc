## Deviations and execution notes

* The protocol was followed as registered. There was no arm, metric or seed selection, no early stopping and no checkpoint selection.
* All fits ran on CPU (CUDA was slower for these tiny sequential GRU cells under deterministic algorithms). The released fits ran on CUDA.
* One seed-7 job (RGB K=1) died from a host-wide out-of-memory error and was rerun from scratch. The CPU fits are deterministic: the rerun reproduced the crashed run's rotation-0 losses bit for bit.
* For throughput, fusion arms were split across processes with a wrapper that restricts `run.ARMS`. Every fold re-seeds, so outputs are identical to `run fusion --seed S [--reference]`.
* After all fits finished, the package was `ruff format`-ed (AST-preserving) and one `-> None` annotation was added. Receipts record the source hashes that were executed (`EXECUTED_SOURCES.json`).
* Seconds MAE uses the released output map `phase_to_ttc`, which clamps |T̂| ≤ 60 s.

## Limits

* Internal control on development folds (eAP TRAIN40 OOF). It is not a test result, and the levels are not comparable to the leaderboard (35.80 vs 45.03).
* Producers are fixed and were themselves OOF-generated. Fusion-training inputs come from producers that saw the test block (second-order leakage, shared by all arms). The recipe was developed at K=8, which favours the released arm.
* Even K=1 is not Garl-TTC's two-frame regime. Each observation already integrates ≈200 ms (RGB, 3 frames) or ≈300 ms (event windows) inside the single-observation producers. The ablation removes refiner history only.
* Garl-TTC is not retrained with longer history.
* RGB history is at 100 ms spacing and event history at 50 ms, so the same K means different milliseconds per modality. K=8 is effectively 5 RGB and 7 event slots.
